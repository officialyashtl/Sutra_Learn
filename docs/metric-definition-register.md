## 1. Architectural Mandate: Single Source of Truth

This register governs all mathematical, learning, and progress metrics within SUTRA LEARN. All frontend views (`StudentHome`, `StudentPathway`, `StudentProgress`, `StudentInsights`, `TeacherDashboard`, `TeacherLearners`, `TeacherLearnerProfile`, `TeacherInsights`, `TeacherInterventions`) MUST consume metrics exclusively generated by the canonical backend service:
- `app.services.metrics.calculate_learner_metrics` via `GET /api/v1/learners/{id}/metrics`
- `app.services.metrics.calculate_cohort_metrics` via `GET /api/v1/teacher/metrics`

No frontend component is permitted to independently calculate accuracy or mastery.

## 3. Discrepancy Reconciliation Analysis

### Historical Defect Identified
Previously, `StudentHome.tsx` and `StudentProgress.tsx` computed independent client-side aggregations:
- `StudentHome.tsx` calculated:
  `const progressList = Object.values(progressMap);`
  `const totalSubmissions = progressList.reduce((acc, p) => acc + (p.total_attempts || 0), 0);`
- `StudentProgress.tsx` calculated:
  `const totalSubmissions = progressList.reduce(...);`
  AND fetched `GET /api/v1/learners/{id}/attempts`, where length was displayed as "Total Submissions".

When an unattempted concept lacked a row in `concept_progress`, or when an attempt had been submitted but `concept_progress` was not yet updated, Home and Progress reported differing attempt counts.

### Definitive Architectural Solution
Both `StudentHome.tsx` and `StudentProgress.tsx` (as well as `StudentInsights.tsx`) now consume canonical metrics directly from `GET /api/v1/learners/{id}/metrics`. This endpoint queries the authoritative `attempts` table and `concept_progress` table within a single atomic database transaction, guaranteeing zero metric drift across all views.
